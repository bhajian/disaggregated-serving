## Changing topology is one custom-resource edit

Both variants of a model use the same graph name (`metadata.name`). Applying the
other variant updates that one object, and the operator reconciles it: it removes the
`worker` component and creates `prefill` + `decode` components (or the reverse). The
lab path instead swapped Deployment files.

```bash
kubectl --context "$KUBE_CONTEXT" apply -k deploy/overlays/production/nemotron-3-nano-h200/disaggregated
kubectl --context "$KUBE_CONTEXT" -n nemotron-3-nano get dynamographdeployment nemotron-3-nano -o yaml
diff <(kustomize build deploy/base/dynamo/nemotron-3-nano/aggregated) \
     <(kustomize build deploy/base/dynamo/nemotron-3-nano/disaggregated)
```

The diff is: the topology annotation; the frontend's `--router-min-initial-workers`
(number of routable workers) and probe requirement (`backend` vs `backend,prefill`);
and the worker component, replaced by `prefill` (with `--disaggregation-mode prefill`,
NIXL, a concurrency cap and no CUDA graphs) and `decode`
(`--disaggregation-mode decode`). Everything else is identical.

## What differs from the measured lab configuration

Engine flags start from the manifests that produced `results/`
(`deploy/sites/nebius-h200-2x8/*/lab/as-measured`). `tests/test_graphs.py` fails if any
other flag changes. Added flags:

| Flag | Why |
| --- | --- |
| `--gc-threshold` | raise CPython GC thresholds so generation-2 collections (0.34-0.45 s output pauses every ~11 s in the 8K/128K study) run ~100x less often; confirmed by experiments/04-reliability |
| `--router-min-initial-workers` | frontend waits for every worker before routing, so the first registered worker does not absorb the initial burst |
| `--router-decode-active-request-weight` | count active requests in the KV-router cost; with unique prompts the default (0) balances on tokens only and produced 152/120/120/120 in the 8K/128K study |
| `--router-replica-sync` | two frontend replicas share router state |
| `--max-running-requests (prefill)` | cap concurrent prefill requests to bound host staging memory; the prefill pod swung 104-308 GiB during a 384-request burst and was OOM-killed at its 384 GiB limit (8K/128K diagnostics) |
| `--kv-events-config` | fixed in-pod port 5557; the lab used per-node host ports because of hostNetwork |

Pod-level changes from the lab: no `hostNetwork` and no privileged mode (`IPC_LOCK`
only); host-memory requests and limits per role (prefill 448Gi limit, against an
observed 308 GiB peak); a 2 h startup window and a lenient liveness probe; an
init container that refuses to start if the weights' `DEPLOYED_REVISION` differs from
the pinned revision; a frontend readiness and liveness check that requires
discovered workers; and two frontend replicas with shared router state.
